# Tournament Service — лабораторная работа 3

REST API для управления спортивными турнирами. Проект расширяет предыдущую версию: сущности теперь хранятся в PostgreSQL через Spring Data JPA, а не в коллекциях в памяти.

## Предметная модель

- **User** — пользователь, может быть капитаном или участником команды.
- **Team** — команда с капитаном и списком участников.
- **Tournament** — турнир с лимитом допущенных команд и статусом `PLANNED` / `IN_PROGRESS` / `FINISHED`.
- **TeamApplication** — заявка команды на турнир со статусом `PENDING` / `APPROVED` / `REJECTED`. Для пары «команда — турнир» допускается одна заявка.
- **Match** — матч турнира между двумя разными командами, обе из которых должны иметь одобренные заявки на этот турнир; статус — `SCHEDULED` / `FINISHED`.

Связи и основные ограничения хранятся на уровне реляционной модели: внешние ключи, обязательные поля, уникальные имя пользователя и email, уникальная заявка на турнир, уникальность участника в команде. Сервис дополнительно проверяет правила переходов состояний.

## Запуск локально

Требуются JDK 21+, Maven и Docker Compose.

1. Скопируйте `.env.example` в `.env`. Это локальный файл конфигурации; не добавляйте `.env` в Git.
2. Установите свои значения для `POSTGRES_PASSWORD` и `DB_PASSWORD`. `DB_PASSWORD` используется и для создания роли приложения, и для подключения Spring Boot. Значения в `.env.example` демонстрационные — перед использованием замените их. Скрипт `db/init/01-init-database.sh` создаёт отдельную роль приложения и таблицы от имени администратора PostgreSQL. Роль приложения получает только `USAGE` на схему и права `SELECT/INSERT/UPDATE/DELETE` на таблицы и необходимые права на последовательности; `CREATE` и владение схемой приложению не выдаются. Hibernate работает в режиме `ddl-auto: validate` и не меняет структуру БД. Пароль роли передаётся через переменные окружения, а не хранится в SQL-файле.
3. Выполните `docker compose up --build` из корня проекта. На этапе сборки Docker запускает `mvn package`, включая автоматические unit-тесты; если тест или компиляция не пройдут, сборка завершится ошибкой. После успешной сборки Compose поднимет PostgreSQL и приложение.
4. API доступен по адресу `http://localhost:8080`. Демонстрационные данные загружаются из `src/main/resources/data.sql`; две команды в них уже допущены к турниру, поэтому стартовый матч соответствует правилам допуска.

Скрипты из `db/init` выполняются только при первом создании volume. Для повторного запуска сценария на исходных демонстрационных данных используйте `docker compose down -v`, затем `docker compose up --build`. Команда `down -v` удаляет локальные данные БД.

### Переменные окружения

`DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `SERVER_PORT`. В Compose отдельно задаются `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` для первоначального владельца БД. Сервис подключается отдельной ролью `tournament_app`, не владельцем базы.

## Проверка автоматическими тестами

Из корня проекта выполните `mvn test`. Unit-тесты проверяют ключевые положительные и отрицательные сценарии сервисов: допустимость матчей только между одобренными командами, запрет редактирования после перехода состояния, лимит заявок и невозможность подачи/переноса/удаления заявки в недопустимом состоянии. Для проверки блокировок между конкурентными запросами нужен запуск на PostgreSQL; одних unit-тестов для доказательства конкурентной корректности недостаточно.

## REST API

CRUD-ресурсы:

- `/api/users`
- `/api/teams`
- `/api/tournaments`
- `/api/team-applications`
- `/api/matches`

У ресурсов доступны операции `GET` списка, `GET /{id}`, `POST`, `PUT /{id}`, `PATCH /{id}`, `DELETE /{id}`. Форматы тел для создания и изменения показаны в коллекции `postman/Tournament-Service-Lab3.postman_collection.json`.

## Пять бизнес-операций

1. `POST /api/team-applications/{id}/approve` — принимает ожидающую заявку, только пока турнир запланирован и лимит команд не исчерпан. Проверяет заявку и состояние турнира.
2. `POST /api/team-applications/{id}/reject` — отклоняет только ожидающую заявку до начала турнира.
3. `POST /api/tournaments/{id}/start` — запускает запланированный турнир, только если допущены минимум две команды.
4. `POST /api/matches/{id}/finish` — завершает запланированный матч только в турнире со статусом `IN_PROGRESS`.
5. `POST /api/teams/{teamId}/members/{userId}` — добавляет существующего пользователя в команду; повторное добавление отклоняется.

CRUD-операции не считаются бизнес-операциями. Бизнес-правила проверяют состояние связанных сущностей; при недопустимом переходе API возвращает `400 Bad Request`, а при отсутствии сущности — `404 Not Found`.

## Сценарий проверки

Откройте Postman и импортируйте коллекцию. Запустите папку «Основной сценарий — создание данных и 5 бизнес-операций» строго по порядку: коллекция сама создаст четыре пользователя, турнир, три команды и три заявки, сохранит ID ответов в переменные, одобрит две заявки, отклонит третью, создаст матч между двумя допущенными командами и затем выполнит запуск турнира, завершение матча и добавление участника. Сценарий не зависит от фиксированных ID в `data.sql`; повторный запуск создаёт новые уникальные записи. Внутри основного сценария также проверяется, что матч с недопущенной командой отклоняется. После него запустите папку отрицательных сценариев: повторное одобрение уже обработанной заявки и подача заявки после старта турнира должны вернуть `400 Bad Request`. CRUD-запросы каждой сущности находятся в отдельной папке и предназначены для выборочной проверки — не запускайте всю CRUD-папку подряд, поскольку некоторые примеры изменяют или удаляют данные.

## Передача проекта в GitHub Влада

Архив для передачи не содержит `.git`, чтобы не переносить чужую историю и настройки удалённого репозитория. После распаковки Влад может открыть папку как Maven-проект в IntelliJ IDEA. Чтобы отправить проект в свой GitHub, из корня проекта выполните:

```bash
git init
git add .
git commit -m "Lab 3: PostgreSQL and business operations"
git branch -M main
git remote add origin https://github.com/<владелец>/<репозиторий>.git
git push -u origin main
```

Замените URL на адрес именно его репозитория. Если репозиторий уже склонирован на ПК Влада, безопаснее скопировать файлы проекта в папку клонированного репозитория, не копируя `.git`, затем выполнить `git add`, `git commit` и `git push`.
